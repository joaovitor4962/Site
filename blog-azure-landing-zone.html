Azure Landing Zone: do conceito à operação em produção

Como estruturamos management groups, policies, blueprints, conectividade hub-spoke e guardrails para um ambiente governável desde o dia 1.

10 min de leitura08/10/2026IT Cloud Solutions

Por que Landing Zone?

A maioria das empresas entra no Azure criando recursos direto na subscription raiz. Resultado: sprawl, custos invisíveis, segurança frágil, auditoria impossível. A Azure Landing Zone (ALZ) resolve isso com uma arquitetura de referência baseada no Cloud Adoption Framework (CAF).

Nossa Implementação

1. Hierarquia de Management Groups

Root MG
├── Platform
│   ├── Connectivity
│   ├── Identity
│   └── Management
├── Landing Zones
│   ├── Corp
│   ├── Online
│   └── Sandbox
└── Decommissioned

Cada MG herda policies do pai. Platform = infra compartilhada (Firewall, DNS, ExpressRoute, Azure AD). Landing Zones = workloads de negócio isoladas.

2. Policy-as-Code (Azure Policy + Bicep)

  • Deny: recursos sem tags obrigatórias, discos não criptografados, storage público, VMs sem backup
  • Audit: SKUs não aprovadas, regiões não permitidas, NSGs muito permissivas
  • DeployIfNotExists: Diagnostics → Log Analytics, Microsoft Defender for Cloud, Backup
  • Initiative (Policy Set): CAF Foundation, PCI-DSS, ISO 27001, CIS Azure Foundations

3. Conectividade Hub-Spoke

Hub Central (Connectivity MG): Azure Firewall Manager, VPN Gateway, ExpressRoute, Azure Bastion, Private DNS Zones. Spokes (Landing Zones): VNet peering para o hub, UDR forçando tráfego via Firewall, NSGs por subnet.

4. Guardrails Operacionais

  • Resource Locks: CanNotDelete em recursos de plataforma (Firewall, Log Analytics, Key Vault)
  • Blueprints/Deployment Stacks: provisionamento repetível de spokes novos (infra + policies + RBAC)
  • Cost Management: budgets por MG, alertas 80%/100%, showback via Power BI
  • Identity: PIM para roles privilegiadas, Conditional Access, break-glass accounts
